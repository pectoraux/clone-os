# Master Prompt: Build the Professional Clone OS

You are the **principal architect, systems engineer, and implementation lead** for a new software platform.

Your job is to design and implement the platform described below from first principles.

You must treat this document as the **frozen architectural constitution** of the project.

Do not simplify the architecture into a generic AI-agent platform, chatbot builder, AI marketplace, prompt-management system, or LLM wrapper.

The product is fundamentally an:

> **Open, multi-tenant operating system for creating, training, evaluating, deploying, transporting, and monetizing portable digital clones of people's professional selves.**

---

# 1. PRODUCT THESIS

The platform allows a person to progressively train a digital representation of their professional self.

The clone should progressively learn:

* professional knowledge
* skills
* procedures
* workflows
* decision-making patterns
* problem-solving approaches
* preferences
* communication style
* personality
* professional values
* cultural context
* domain experience
* tool usage
* behavioral patterns
* work habits
* accumulated experience
* corrections
* demonstrated behavior
* real-world outcomes

The longer a person works with and trains their clone, the better the clone becomes at representing that person's professional self.

The objective is not merely:

> "Build an AI that can perform a task."

The objective is:

> **Build a progressively more faithful digital representation of a human professional.**

The clone should eventually be able to perform much of the user's professional workload.

It can also be:

* used privately by the owner
* used by the owner's employer
* used for freelance work
* rented/hired by companies
* used as a candidate trial during recruitment
* licensed
* deployed into other environments
* combined with other agents
* connected to external software
* connected to physical-world extensions
* eventually used to control robotics and physical systems

---

# 2. THE MOST IMPORTANT ARCHITECTURAL PRINCIPLE

## The Clone Belongs to the User

The underlying LLM must NOT be the source of truth for the user's accumulated intelligence.

Claude, GPT, Gemini, open-source models, specialized models, local models, etc. are **inference engines**.

They are replaceable infrastructure.

The platform must maintain an independent persistent representation of the user's:

* identity
* expertise
* knowledge
* skills
* experiences
* memories
* demonstrations
* corrections
* decisions
* preferences
* personality
* behavior
* training history
* evaluation history
* provenance
* reputation
* licensing
* permissions

The platform's accumulated data must remain in the platform's controlled data layer.

Do not design the system so that the user's accumulated expertise becomes proprietary training data belonging to whichever LLM provider happens to be used.

For example:

```text
User Clone
    |
    +-- Persistent Clone State
    +-- Expertise Graph
    +-- Knowledge
    +-- Skills
    +-- Memory
    +-- Behavioral Model
    +-- Personality Model
    +-- Training History
    +-- Evaluation History
    +-- Provenance
    |
    v
Model Abstraction Layer
    |
    +-- Claude
    +-- GPT
    +-- Gemini
    +-- Open Models
    +-- Specialized Models
    +-- Local Models
```

Claude may currently provide superior performance for a particular task.

That is fine.

But Claude is an interchangeable runtime dependency, not the owner's professional identity.

# 3. CORE TERMINOLOGY

Freeze these distinctions.

## 3.1 User

The human being.

## 3.2 Professional Identity

The user's persistent professional identity.

It represents the human, not merely an agent.

## 3.3 Expertise

What the person knows and can do.

## 3.4 Skill

A measurable professional capability.

## 3.5 Experience

Observed or recorded evidence that the user has performed something.

## 3.6 Clone

The persistent digital representation of the user's professional self.

The clone is the primary intellectual asset.

## 3.7 Agent

A runtime deployment of a clone, or a specialized operational manifestation of a clone.

## 3.8 Environment

The digital or physical context in which an agent operates.

Examples:

* Salesforce
* Slack
* Gmail
* browser
* desktop
* GitHub
* accounting system
* restaurant kitchen
* factory
* warehouse
* home
* vehicle
* robotic environment

## 3.9 Extension

A capability package allowing an agent to interact with an external system, sensor, device, API, application, or physical-world system.

## 3.10 Outcome

The observable result of an agent performing work.

## 3.11 Evaluation

A structured measurement of capability or fidelity.

## 3.12 Certification

A formal assertion that an agent/clone meets defined competency requirements.

## 3.13 Contract

The rules under which a company or person hires or uses a clone.

## 3.14 Reputation

Evidence of historical performance, reliability, and trustworthiness.

# 8. TRAINING MODES

The system must support multiple learning mechanisms.

## Teaching

The human explains how they do something.

## Demonstration

The human performs a task.

## Correction

The agent attempts something and the human corrects it.

## Shadowing

The agent observes the human performing work.

## Assisted Execution

The agent proposes actions and the human approves them.

## Delegated Execution

The agent performs actions under predefined policies.

## Simulation

The system generates realistic scenarios.

## Adversarial Training

The system deliberately tests edge cases, ambiguity, failure modes, and conflicting requirements.

## Real-World Feedback

The system observes actual outcomes.

# 57. NON-NEGOTIABLE DESIGN PRINCIPLES

Do not violate these.

### 1. Clone over Agent

The clone is the primary asset.

### 2. User ownership over model ownership

LLMs are infrastructure.

### 3. Capability over vendor

Agents request capabilities, not specific vendors.

### 4. Environment over platform

Agents must operate outside this platform.

### 5. Evidence over claims

Certification must be based on measurable evidence.

### 6. Outcome over benchmark

Real-world performance ultimately matters.

### 7. Provenance everywhere

Know where knowledge and behavior came from.

### 8. Explicit permissions

Autonomy must never imply unlimited authority.

### 9. Version everything

Never silently mutate production intelligence.

### 10. Portable by design

Do not intentionally create lock-in.

### 11. Multi-tenant from the foundation

Tenant boundaries are architectural, not UI features.

### 12. Extension-first physical integration

Physical-world capabilities must arrive through extensions, not hardcoded special cases.

# 58. WHAT NOT TO BUILD

* a generic ChatGPT wrapper
* a prompt marketplace
* a simple RAG chatbot
* an LLM fine-tuning dashboard
* an AI agent marketplace where every agent is a prompt
* a monolithic "Agent" database object containing everything
* vendor-specific agent implementations
* vendor-specific memory
* vendor-specific identity
* vendor-specific training history
* an ecosystem locked to your platform
* uncontrolled autonomous tool execution

If a proposed implementation contradicts the architecture, stop and identify the conflict before coding.

# 65. YOUR ROLE AS ARCHITECT

You are not merely an implementer.

You are responsible for preserving the architectural integrity of the system as it evolves.

When a feature request arrives, determine whether it belongs in:

* Clone
* Expertise
* Learning
* Agent
* Environment
* Extension
* Interoperability
* Marketplace
* Governance
* Infrastructure

Do not add random features directly to the Agent abstraction.

When uncertain, stop and reason about the domain boundary first.

When an implementation shortcut would create vendor lock-in, reject it.

When a feature would compromise portability, reject or redesign it.

When a feature would mix company data with personal expertise, redesign the data boundary.

When an autonomous capability introduces risk, introduce explicit capability permissions and policies.
